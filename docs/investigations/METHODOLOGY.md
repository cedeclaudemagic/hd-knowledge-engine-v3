# Investigation Methodology

## The First Principles Approach

This document defines the methodology for deriving Human Design structures from geometric necessity.

---

## The Core Question

For any HD structure, we ask:

> **Does this structure emerge from geometric necessity, or is it transmitted content?**

### Geometric Necessity (Derivable)
- The structure MUST be this way given the mathematical constraints
- No other configuration is possible
- Multiple independent derivation paths converge on the same result
- Example: 8 trigrams = cube vertices (no other 3-bit binary arrangement works)

### Transmitted Content (Empirical)
- The structure COULD be otherwise — this is one valid choice among many
- Selection was made by tradition/transmission, not mathematical requirement
- The geometry *constrains* but doesn't *determine*
- Example: Specific gate names and keywords (vocabulary layer)

### The Boundary
- Currently ~40% of planetary assignments appear derivable
- This boundary marks where geometric necessity ends and transmission begins
- The boundary itself is a finding — but it's a **current state**, not a permanent conclusion

## The Inductive Pattern

### Step 1: State the Question Precisely

**Bad:** "Why does the Solar Plexus work this way?"
**Good:** "What geometric necessity, if any, determines that the Solar Plexus operates at position -2 (voltage)?"

The question must be:
- Specific (one structure at a time)
- Testable (can be confirmed or ruled out)
- Geometric (asks about mathematical necessity)

### Step 2: Gather What's Already Proven

Before investigating, consult:

1. **DERIVATION-STATUS-MAP.md** — Is this already proven?
2. **Cross-Reference Matrix** — Where has this been discussed?
3. **Framework folder** — Does proven work already address this?

**Never re-derive what's already proven.**

### Step 3: Identify the Geometric Context

What proven structures surround this investigation?

| Layer | Proven Structure | Relevance |
|-------|------------------|-----------|
| Above | What contains this? | Constraints from above |
| Parallel | What's at the same level? | Patterns to match |
| Below | What does this contain? | Must accommodate |

Example for Variable investigation:
- Above: Line level (octahedron vertices) — proven
- Parallel: Profile (octahedron × 2 distances) — proven  
- Below: Color-Tone-Base (6-6-6-5) — structure proven, meanings outstanding

### Step 4: Hypothesise Geometric Mechanism

Form a specific hypothesis:

> "If [geometric structure X] determines [HD element Y], then [testable prediction Z] should hold."

The hypothesis must:
- Be falsifiable
- Make specific predictions
- Connect to proven framework

### Step 5: Test Against Data

Apply the hypothesis to HD data:

1. **Count matches** — How many instances follow the pattern?
2. **Identify exceptions** — What doesn't fit?
3. **Calculate significance** — Is this better than chance?

Statistical thresholds:
- **>95% match** = Strong candidate for PROVEN
- **70-95% match** = MAPPED (pattern real, exceptions need explanation)
- **40-70% match** = PARTIAL (something there, incomplete understanding)
- **<40% match** = Likely NOT geometrically determined

### Step 6: Verify Independence

A derivation is strongest when:
- Multiple paths reach the same conclusion
- The structure is overdetermined
- Different researchers/sessions converge

Check: Does this derivation connect to other proven structures? If isolated, be cautious.

### Step 7: Document and Classify

| Result | Classification | Destination |
|--------|---------------|-------------|
| Geometric necessity proven | PROVEN | `/docs/framework/` |
| Pattern found, not fully derived | MAPPED | Stay in `/docs/investigations/` |
| Confirmed as transmitted | EMPIRICAL | `/docs/investigations/boundaries/` |
| Inconclusive | OUTSTANDING | `/docs/investigations/active/` |

## What Counts as "Proven"

A derivation is PROVEN when:

1. ✓ The geometric mechanism is explicit (not just correlation)
2. ✓ The structure is necessary (no other configuration works)
3. ✓ It connects to the proven framework (not isolated)
4. ✓ Exceptions are explained (or there are none)
5. ✓ Multiple verification paths converge

A derivation is NOT proven if:

- ✗ It's a correlation without mechanism
- ✗ Alternative structures would also work
- ✗ It contradicts proven framework
- ✗ Exceptions are ignored or hand-waved
- ✗ Only one approach supports it

## Common Pitfalls

### 1. Confusing Correlation with Causation
"These numbers match" ≠ "This is geometrically necessary"

Ask: WHY do they match? What mechanism requires it?

### 2. Forcing the Framework
If the data doesn't fit, don't force it. Transmission content is a valid finding.

### 3. Ignoring Exceptions
Every exception needs explanation. If you can't explain it, the derivation is incomplete.

### 4. Re-deriving Proven Work
Always check existing work first. The framework folder exists for a reason.

### 5. Isolated Derivations
A derivation that doesn't connect to anything else is suspicious. The framework is interconnected.

## Output Standards

### File Naming
```
INVESTIGATION-[TOPIC]-[DATE].md
SYNTHESIS-[TOPIC].md
BRIEF-[TOPIC].md
```

### Required Sections

Every investigation output must include:

1. **Question** — Precisely stated
2. **Hypothesis** — Specific, testable
3. **Method** — How tested
4. **Results** — What was found (with numbers)
5. **Classification** — PROVEN / MAPPED / EMPIRICAL / OUTSTANDING
6. **Connection** — How this relates to proven framework
7. **Next Steps** — If incomplete, what remains

| MAPPED | Stay in `/docs/investigations/active/` |
